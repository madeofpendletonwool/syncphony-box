# ADR 0013: The x86-64 box, a live/installer ISO

- Status: Accepted
- Date: 2026-10-15
- Deciders: x86 image issue (MAD-846), widening MAD-797's "x86 mini-PC
  images: out of scope"

## Context

Until now the box was Pi-only: arm64, built by pi-gen (ADR 0001). Plenty
of rooms already have an old PC or a mini-PC next to the TV, and there
was nothing for them. The goal: any x86-64 PC can be a box with the same
behavior as a Pi (the kiosk, the audio, `/data`, the read-only root, the
updates), from one download.

Two things had to stay true. The Pi image must not fork into a second
copy of the box's setup, and nothing about how a Pi works may change.

## Decision

### One deliverable: a hybrid ISO with two boot entries

`syncphony-box-<version>-amd64.iso` is a hybrid ISO: it boots from a DVD
or written straight to a USB stick (`dd`, Etcher, Imager's "Use custom"),
so there is no separate x86 `.img`. Its one GRUB menu serves both
firmware types, UEFI and legacy BIOS:

1. **Syncphony Box (live).** The box, running from the medium. live-boot
   gives it the read-only squashfs root with writes going to RAM, the
   overlay the Pi gets from its own initramfs script. A partition
   labelled `syncphony-data` on the stick becomes `/data`, so pairing
   and setup survive reboots. Without one, the box works and forgets
   everything at power-off.
2. **Install Syncphony Box to disk.** Runs the installer.

Secure Boot is not a goal. The ISO and installed boxes boot unsigned
GRUB, so Secure Boot has to be off.

### Builder: Debian live-build on Trixie

live-build is Debian's own tool for exactly this artifact (it builds
Debian's official live images): debootstrap, a chroot stage with hooks,
a squashfs, live-boot's initramfs, and the ISO with GRUB for both
firmware types. The alternatives were worse fits. mkosi makes disk
images, not a live ISO with an installer. A hand-rolled debootstrap +
grub-mkrescue would reimplement live-build. And the Pi's base is
Raspberry Pi OS Trixie, so Debian Trixie on x86 keeps both boxes on one
Debian release, one Chromium and one PipeWire.

`./build-iso.sh` (`make iso`) runs `lb build` in a privileged
`debian:trixie` container, so any Linux host with Docker can build it,
the way `./build.sh` runs pi-gen in its container. CI builds it on an
x86 runner next to the Pi image on an arm64 one.

### The shared stage layer: `rootfs/`

The old `stage-syncphony/*/00-run.sh` scripts mixed two things: what
makes a Debian root a box, and pi-gen's way of doing it (`on_chroot`,
`${ROOTFS_DIR}`, `/boot/firmware`). They are split:

- **`rootfs/customise.sh PLATFORM DEB`** runs *inside* the target root,
  as root, with the target at `/`. It installs `packages/common.list`
  plus `packages/<pi|x86>.list`, then the `syncphony-box` .deb, then
  `steps/*.sh` in order: the kiosk user's audio, the read-only-root
  links and fstab's `/data` line, timesyncd, NetworkManager, the
  slimming. It knows nothing about either builder.
- **pi-gen wrapper** (`stage-syncphony/`): `00-customise` copies
  `rootfs/` and the .deb into the chroot and runs
  `customise.sh pi` through `on_chroot`. `01-pi-boot` does what only a
  Pi has: `cmdline.txt` (quiet, `boot=overlay`, `grow-data`, no
  `resize`), `config.txt`, the read-only FAT in fstab, `syncphony.txt`
  onto the boot partition, `rpi-resize` off.
- **live-build wrapper** (`x86/live`): a chroot hook runs
  `customise.sh x86`, resolves the `/data` line to the label, enables
  the x86-only units and rebuilds the initramfs. A binary hook writes
  the ISO's boot menu. `x86/root` holds the image-only files: the
  installer, its units and templates, and the live session's
  `/boot/firmware`.

Package lists use the format both builders already share (one name per
line, `#` comments), but `customise.sh` installs them itself
(`--no-install-recommends`, like pi-gen), so the lists live in one place.

The split itself doesn't change what lands in the Pi image: the same
packages, files, links and units, in the same order. Two package changes
made for x86 reach the Pi too, both no-ops there: the initramfs hook
(the Pi's initramfs already had `e2fsck` and the overlay module) and the
update unit's live-session condition. The smoke test's Pi checks are the
same ones as before.

### What changed for x86, and how

- **Boot partition.** An installed box's EFI system partition (FAT32,
  label `SB-BOOT`) is mounted at `/boot/firmware`, read-only, exactly
  where the Pi's FAT is. So `syncphony.txt` lives on it, and boxd's
  rw-remount writes (the setup form, `resolution=`) follow it there with
  no code change.
- **`cmdline.txt` becomes `cmdline.cfg`.** GRUB can't read a plain file
  into the kernel command line, so the installer writes
  `/boot/firmware/cmdline.cfg`, a GRUB script with one line
  (`set syncphony_cmdline="boot=overlay quiet ..."`), and `grub.cfg`
  sources it. boxd uses `cmdline.cfg` when it exists and `cmdline.txt`
  otherwise, and edits only that `set` line. The Pi path is untouched.
  The live session has neither file, and boxd skips display settings
  there instead of writing a file nothing reads and rebooting.
- **`config.txt`** has no x86 counterpart: the firmware splash is the
  PC's own, and GRUB's menu is hidden (`timeout_style=hidden`).
- **Read-only root.** The same initramfs overlay script as the Pi
  (`boot=overlay`), the same `/data`, the same `syncphony-box chroot` and
  nightly update. A new initramfs hook in the package copies `e2fsck` in.
  initramfs-tools only adds it when fstab has an ext4 root line, and the
  live-built root has none. One initramfs serves both the live session
  (`boot=live`) and the installed box (`boot=overlay`).
- **Thermals.** boxd reads `/sys/class/thermal` when there is no
  `vcgencmd`: the CPU package zone (`x86_pkg_temp`) first, then other
  CPU/SoC zones, then ACPI's. A PC has nothing like the Pi firmware's
  throttling bitmap, so `/v1/info` reports `temperatureC` only, rather
  than claiming "not throttled".
- **Audio.** `audio-setup`'s HDMI markers are vc4 names. Where no vc4
  sink exists at all, `hdmi`/`hdmi2` are the first and second built-in
  HDMI/DisplayPort sinks, and `analog` is the built-in analog output. A
  Pi with HDMI0 absent still never falls back to HDMI1.
- **Watchdog.** `RuntimeWatchdogSec` arms whatever `/dev/watchdog` the
  PC has (iTCO and similar). A PC without one logs it and runs on.
- **CEC.** Most PC GPUs can't send CEC. boxd already runs without
  `/dev/cec*`, so the box simply has no CEC there. A Pulse-Eight USB
  adapter is a later issue.
- **Firmware.** `packages/x86.list` names it: GPU (Intel, AMD),
  Wi-Fi (Intel, Realtek, Atheros), the SOF audio DSPs of recent Intel
  machines with the UCM profiles PipeWire needs, and microcode.
  live-build's own all-firmware switch stays off.

### The installer: a script on tty1

`syncphony-install` is a bash script with `whiptail` dialogs, run on
tty1 by `syncphony-installer.service` when the install entry put
`syncphony.install` on the kernel command line. Drop-ins keep the kiosk,
boxd and `/data` off in that boot. It:

1. offers every writable disk big enough, except the one the live
   system booted from, and asks twice before erasing it;
2. optionally creates an admin user with sudo. A PC has no Imager to make
   one, and without one there is no login for SSH or
   `syncphony-box chroot`;
3. partitions GPT: a 1 MiB BIOS boot partition (GRUB's core image on a
   BIOS machine), the ESP (`SB-BOOT`, 256 MiB), root (ext4,
   `syncphony-root`, twice the image's size and at least 4 GiB, so
   nightly updates have room), and `syncphony-data` taking the rest. The
   Pi's three partitions plus BIOS boot, so `/data` is full size from the
   start and `grow-data` isn't used;
4. copies the live system's *pristine* root (live-boot's read-only
   squashfs mount, not the running overlay), plus the kernel and
   initramfs from the medium if the squashfs lacks them, and writes
   fstab by UUID;
5. runs `grub-install` twice, for UEFI (`--removable --no-nvram`: the
   fallback path every UEFI firmware boots, no NVRAM entry to go stale)
   and for BIOS, both into the ESP, then writes `grub.cfg` and
   `cmdline.cfg` from templates;
6. lays out `/data` (the same directories `add-data-partition.sh` makes
   for the Pi image) and puts `syncphony.txt` on the ESP.

Only the `-bin` GRUB packages are installed (`grub-pc-bin`,
`grub-efi-amd64-bin`). The full `grub-pc`/`grub-efi-amd64` packages
would try to reinstall the bootloader on the real root during a nightly
update. On an installed box, the bootloader is the installer's and stays
put.

The issue allowed the disk picker to be a boxd screen in the kiosk. A
tty1 script is less code to get wrong for a step that runs once per
machine, needs no network and no phone, and works on a PC whose GPU
Chromium can't drive yet. A boxd screen can replace it later without
changing the disk layout.

### The live session's /boot/firmware

The live session boots from read-only media with no boot partition.
`syncphony-live-boot.service` makes one for boxd. With `/data` mounted
from the stick, `/boot/firmware` is a bind mount of
`/data/boot-firmware`, so the setup form's writes persist. Without it,
`/boot/firmware` is on the RAM overlay with the template. The nightly
update is off in a live session (`ConditionKernelCommandLine=!boot=live`
on its unit): there is no real root to update.

## Consequences

- Releases carry the ISO next to the Pi image, and the apt repo carries
  an amd64 `syncphony-box` next to the arm64 one, so installed PCs update
  the way Pis do. The Imager listing stays Pi-only (Imager's device
  list is Pi boards).
- The release now waits for two image builds. The ISO job runs on a
  standard x86 runner in about the time the Pi job takes.
- `/data` is found by label everywhere (the Pi's initramfs and the x86
  live session). With two `syncphony-data` partitions attached (the
  live stick still plugged into an installed box), which one mounts is
  undefined. The installer says to remove the stick.
- Disks over 2 TiB work (GPT), and the 4 GiB root minimum means a disk
  smaller than about 6 GB isn't offered.
- `resolution=`/`rotate=` keep the Pi's `video=HDMI-A-1:` token. On a PC
  the connector may be `DP-1` or `HDMI-A-2`, and the setting then does
  nothing. Picking the connector is a follow-up if PCs need it.
- No VM image (qcow2/raw for Proxmox) yet. It can be made from the same
  squashfs later.
- CI can't boot the ISO. The VM procedures that check the done-when
  (live boot on UEFI and BIOS, install, reboot still paired) are in
  `docs/testing.md`.
